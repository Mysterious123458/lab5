# Городские обращения о благоустройстве с JWT access/refresh

Учебное приложение для лабораторной работы 5 по РБПО, вариант 26. Поверх ролевой модели работы 4 добавлены пары JWT-токенов (access и refresh, подпись HS256), обновление пары и серверный учёт refresh-сессий в таблице `user_sessions`.

Номер студенческого билета задан в `spring.application.name`: `24074`.

## Пары токенов

- Оба токена — JWT с подписью HS256. Ключ берётся из `security.jwt.secret` (переменная `JWT_SECRET`), минимум 32 байта: с более коротким секретом приложение не запускается.
- Время жизни задаётся настройками `security.jwt.access-ttl` и `security.jwt.refresh-ttl` (по умолчанию 15 минут и 12 часов).
- Каждая выдача создаёт новые `jti`. Обязательные claims: `sub` (email), `type` (`access` или `refresh`), `jti`, `iat`, `exp`. Проверка включает подпись, срок действия и `type`: access-фильтр принимает только `access`, обработчик обновления — только `refresh`.
- `exp` в токене и срок в записи сессии совпадают с точностью до секунды.

## Сессии

- Таблица `user_sessions`: одна строка — одна пара. Колонки `access_token` и `refresh_token` имеют тип `TEXT`, `refresh_token` уникален, `id` — UUID. Статус: `ACTIVE` (пара выдана), `USED` (refresh применён для обновления), `REVOKED` (refresh отозван). Старая строка после обновления сохраняется, для новой пары создаётся новая строка.
- Поиск сессии с блокировкой строки, перевод старой записи в `USED` и сохранение новой пары выполняются в одной транзакции сервиса (`@Transactional`): техническая ошибка сохранения новой пары откатывает всю операцию, включая `USED`.
- Защита от повторного использования refresh: при двух одновременных обращениях с одним токенем пессимистичная блокировка (`SELECT ... FOR UPDATE`) пропускает только один обмен, остальные видят статус `USED`.
- Повторное предъявление ещё не истёкшего refresh со статусом `USED` переводит запись в `REVOKED` и возвращает 401 без новой пары. Изменение сохраняется, несмотря на отказ в HTTP-ответе: сервис бросает проверяемое исключение, которое по правилам отката `@Transactional` не откатывает транзакцию. Для уже отозванной сессии возвращается отказ без изменений.

## Контроллер аутентификации

| Endpoint | Действие | Успешный ответ |
| --- | --- | --- |
| `POST /auth/login` | проверяет логин и пароль, выдаёт пару токенов | 200 |
| `POST /auth/register` | создаёт учётную запись и сразу выдаёт пару | 201 |
| `POST /auth/refresh` | обменивает действующий refresh на новую пару | 200 |

- Успешный ответ каждого эндпоинта: `{"accessToken": "...", "refreshToken": "..."}`.
- `/auth/refresh` не требует access и не принимает пароль повторно: refresh передаётся в JSON-теле, access используется в заголовке `Authorization: Bearer`.
- Сохранены проверки данных из работы 4: политика пароля, уникальность учётной записи и запрет на самостоятельное получение повышенной роли (регистрация всегда создаёт жителя). Регистрация и выдача сессии идут в одной транзакции: если сессию сохранить не удалось, учётная запись не создаётся.
- Коды отказов: 400 — отсутствующее или пустое обязательное поле; 401 — неверные учётные данные, неверный/просроченный/неподходящий по типу refresh, неизвестная/использованная/отозванная refresh-сессия; 409 — повторная регистрация существующего email. Ошибочный ответ не содержит токенов.

## Доступ к API

- Защищённые маршруты принимают access-токен в Bearer-заголовке: фильтр проверяет подпись, срок и `type`, затем загружает учётную запись — роль и состояние (ACTIVE/BLOCKED) всегда актуальны из базы, заблокированный пользователь теряет доступ немедленно.
- HTTP Basic из работы 4 продолжает работать: учётные данные администратора и диспетчера можно передавать как раньше, что удобно для управления ролями.
- CSRF-защита изменяющих запросов сохранена: `GET /api/security/csrf` возвращает токен, изменяющие запросы передают его в заголовке `X-XSRF-TOKEN`.

PostgreSQL 16, установленный локально:

```sql

```

Затем в pgAdmin открыть базу `lab5` и выполнить `db/init.sql`.

```bash

```

Перед запуском приложения задать переменные из `.env.example`:

```text
DB_URL=jdbc:postgresql://localhost:5432/lab5
DB_USERNAME=lab5_app
DB_PASSWORD=lab5_app_password
JWT_SECRET=0f4c1f2e7a9d4b6c8e0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e
```

Пароли и секрет в `.env.example` учебные, для локальной базы. Файл `.env` в репозиторий не входит. Нужен JDK 17 или новее.

```bash
mvn spring-boot:run
```

Приложение слушает `http://localhost:8080`.

## Проверка

Запросы лежат в `postman/lab5.postman_collection.json`. Сначала выполните «JWT → 1. Получить CSRF-токен». Папка «JWT» воспроизводит сценарий задания: вход, обращение к защищённому эндпоинту с access, обмен refresh на новую пару (токены отличаются), повтор старого refresh (401 без пары), продолжение цепочки новым refresh, а также отказы при регистрации и входе.

Проверку таблицы коллекция не выполняет — шаги сценария из задания проверяются в базе вручную (pgAdmin):

1. после `POST /auth/login` в `user_sessions` появляется запись со статусом `ACTIVE`;
2. после `POST /auth/refresh` первая запись получает `USED`, вторая — `ACTIVE`;
3. после повторной отправки старого refresh первая запись становится `REVOKED`, вторая остаётся `ACTIVE`, и новых записей не появляется.
